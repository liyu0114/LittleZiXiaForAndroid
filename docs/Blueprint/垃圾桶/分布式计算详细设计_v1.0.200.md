## 一、核心目标

实现类似CUDA风格的多设备分布式算力：
- GPU A算矩阵乘法 → GPU B算注意力 → 结果汇总
- 多设备算计算单元 → 结果汇总
- 底层并行，不关心任务语义

---

## 二、两种计算模式对比

### 2.1 Hadoop风格（任务级别）

```
任务："分析北京和上海天气"
→ 子任务1："查北京天气"
→ 子任务2："查上海天气"
→ 设备A执行子任务1，设备B执行子任务2
→ 主设备汇总结果
```

| 优点 | 缺点 |
|------|------|
| 实现简单 | 任务必须可拆分 |
| 结果可直接理解 | 不同模型给出不同结果 |
| 类似MapReduce | 强依赖任务语义 |

### 2.2 CUDA风格（计算单元级别）

```
输入文本："分析北京和上海天气"
→ Tokenize → [分词1, 分词2, ...]
→ 拆成计算单元：
  - 计算单元1：Embedding(分词1)
  - 计算单元2：Embedding(分词2)
  - 计算单元3：Attention(中间结果)
  - 计算单元4：FFN(中间结果)
  - ...
→ 设备A算计算单元1
→ 设备B算计算单元3
→ 设备C算计算单元4
→ 结果合并 → Detokenize → 输出
```

| 优点 | 缺点 |
|------|------|
| 不关心任务语义 | 实现复杂 |
| 可并行任意计算单元 | 需要定义标准计算单元 |
| 更底层灵活 | 不同模型架构可能不兼容 |

## 三、技术挑战与可行性

### 3.1 核心挑战

**问题1：不同模型架构能否统一？**

| 模型 | 架构 | 能否统一计算单元？ |
|------|------|------------------|
| DeepSeek | Dense/MoE | 可能 |
| Qwen | Dense | 可能 |
| ChatGLM | GLM | 可能 |
| LLaMA | Dense | 可能 |

**关键问题**：
- 不同模型的Tokenize方式不同
- 不同模型的Embedding维度不同
- 不同模型的Attention实现不同
- 不同模型的FFN结构不同

**结论**：纯CUDA风格在当前技术下**非常难实现**

### 3.2 可行方案

#### 方案A：简化版CUDA（推荐）

```
不拆到Attention/FFN级别
拆到"子任务"级别（类似Hadoop但用CUDA思路）
```

**改进点**：
- 不是"查天气"这样的业务子任务
- 而是"一段文字的处理"这样的计算子任务
- 主设备决定分片策略
- 从设备贡献算力处理自己那片数据

```
输入："请分析这句子的情感"
→ 文本分片：["请分析", "这句", "子的情感"]
→ 
片1 → 设备A处理 → 中间结果
片2 → 设备B处理 → 中间结果
片3 → 设备C处理 → 中间结果
→ 汇总 → 最终结果
```

**优点**：
- 比纯CUDA简单
- 比纯Hadoop灵活
- 不强依赖模型架构

#### 方案B：统一模型（保守）

```
所有设备安装同一个量化模型
设备贡献算力 = 用自己的CPU跑这个模型
```

| 优点 | 缺点 |
|------|------|
| 实现最简单 | 需要每台设备下载模型 |
| 结果一致 | 存储空间 |
| 类似Hadoop | 模型更新 |

#### 方案C：代理模式（最灵活）

```
设备C发请求 → 设备A代理跑DeepSeek → 返回结果
设备C发请求 → 设备B代理跑Qwen → 返回结果
```

| 优点 | 缺点 |
|------|------|
| 完全解耦 | 需要所有设备在线 |
| 模型完全独立 | 网络延迟 |

## 四、详细架构设计

### 4.1 系统架构

```
┌─────────────────────────────────────────────┐
│              主设备（Master）              │
│  ┌─────────────────────────────────┐    │
│  │     Task Decomposer               │    │
│  │  - 文本分片                 │    │
│  │  - 子任务分配               │    │
│  │  - 结果汇总               │    │
│  └─────────────────────────────────┘    │
└─────────────────────────────────────────────┘
              ↓ ↑ 消息
┌────────────────────┐  ┌────────────────────┐
│   设备A（Worker）   │  │   设备B（Worker）  │
│  ┌──────────────┐   │  │  ┌──────────────┐   │
│  │ 本地LLM推理  │   │  │  │ 本地LLM推理  │   │
│  │ - 加载模型  │   │  │  │ - 加载模型  │   │
│  │ - 处理子任务│   │  │  │ - 处理子任务│   │
│  │ - 返回结果 │   │  │  │ - 返回结果 │   │
│  └──────────────┘   │  │  └──────────────┘   │
└────────────────────┘  └────────────────────┘
```

### 4.2 消息协议

```dart
// 任务分发消息
{
  "type": "task_dispatch",
  "taskId": "xxx",
  "subTask": {
    "id": "st_1",
    "input": "请分析这句话的情感",
    "expectedModel": null  // null表示任意模型
  }
}

// 任务结果消息
{
  "type": "task_result",
  "taskId": "xxx",
  "subTaskId": "st_1",
  "result": "积极",
  "confidence": 0.95
}

// 算力贡献消息
{
  "type": "compute_offer",
  "deviceId": "device_a",
  "capability": {
    "modelLoaded": true,
    "modelName": "qwen2.5-0.5b",
    "cpuCores": 8,
    "availableMemory": "4GB"
  }
}
```

### 4.3 设备能力感知

```dart
class DeviceCapability {
  String deviceId;
  bool hasLocalModel;
  String? modelName;  // 如果有本地模型
  int cpuCores;
  String availableMemory;
  int score;  // 算力评分
}
```

**评分公式**：
```
score = cpuCores * 10 + (availableMemory_GB * 5)
        + (hasLocalModel ? 50 : 0)
```

## 五、工作流程

### 5.1 主流程

```
1. 用户输入复杂任务
2. Master分析任务
   ↓
3. 任务分片（拆成N个子任务）
4. 设备能力感知（收集在线设备算力）
5. 子任务分配（根据算力分配）
6. 分发到各设备
7. 各设备并行处理
8. 结果收集
9. 结果汇总
10. 返回最终结果
```

### 5.2 子任务分配策略

```dart
// 简单轮询
assign(subTasks, devices) {
  for (i = 0; i < subTasks.length; i++) {
    device = devices[i % devices.length];
    device.submit(subTasks[i]);
  }
}

// 算力感知分配
assign(subTasks, devices) {
  // 按算力排序，优先分配给强设备
  sortedDevices = devices.sort((a,b) => b.score - a.score);
  for (i = 0; i < subTasks.length; i++) {
    sortedDevices[i % sortedDevices.length].submit(subTasks[i]);
  }
}
```

## 六、实施方案选择

### 推荐：方案A（简化版CUDA）

**理由**：
1. 比纯CUDA简单太多
2. 比Hadoop更灵活（不关心任务语义）
3. 工程上可行

**实现步骤**：
1. 先实现P2P连接和设备发现
2. 实现设备能力感知
3. 实现文本分片器
4. 实现任务分发/结果回收
5. 实现结果汇总

### 备用：方案B（统一模型）

**什么时候用**：
- 方案A验证后发现问题太多
- 需要快速上线

## 七、风险与挑战

| 风险 | 缓解措施 |
|------|--------|
| 不同模型结果不一致 | 只用统一模型方案 |
| 网络延迟太高 | 本地优先，远程辅助 |
| 设备离线 | 任务重分配 |
| 安全问题 | 端到端加密 |
